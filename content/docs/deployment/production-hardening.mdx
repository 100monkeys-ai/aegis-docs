# Production Hardening

import { Callout } from 'fumadocs-ui/components/callout';

This page provides a checklist and guidance for hardening AEGIS platform deployments for production use.

---

## Pre-Deployment Checklist

| Item | Action | Priority |
|------|--------|----------|
| Strong passwords | Replace all default passwords in `.env` (PostgreSQL, Grafana) | Critical |
| SEAL keys | Generate unique Ed25519 keypair (`make generate-keys`) | Critical |
| TLS termination | Deploy Caddy edge proxy with valid certificates | Critical |
| Image pinning | Set `AEGIS_IMAGE_TAG` to a pinned semver, not `latest` | High |
| Registry auth | Configure GHCR credentials (`make registry-login`) | High |
| Firewall rules | Restrict all ports except 80/443 to internal network | High |
| Secrets bootstrap | Initialize OpenBao (`make bootstrap-secrets`) | High |
| Log format | Set `AEGIS_LOG_FORMAT=json` for machine-parseable logs | Medium |
| Monitoring alerts | Verify Prometheus alert rules are active | Medium |
| Backup schedule | Configure automated backups for PostgreSQL and OpenBao | Medium |

## TLS Everywhere

### External TLS

Deploy the [Caddy edge proxy](/docs/deployment/caddy-edge-proxy) for automatic TLS on all public-facing endpoints. Caddy handles certificate issuance and renewal via ACME.

When Caddy (or another trusted-network ingress) terminates TLS upstream of the AEGIS backend pods, those pods bind a non-loopback address inside the trusted Podman network without configuring in-pod TLS. AEGIS refuses to start in this shape unless the operator opts out explicitly via `network.allow_insecure_bind: true` in `aegis-config.yaml`. The default is `false` (fail-closed), and a `WARN` log entry is emitted on every boot when the opt-out is engaged. **Never set this flag on a publicly-exposed host** — see the [Node Configuration reference](/docs/reference/node-config#specnetwork) for the full field description.

### Internal TLS

For high-security environments, enable TLS on internal pod communication:

- **OpenBao**: Set `tls_disable = false` in `openbao-config.hcl` and provide certificate paths
- **PostgreSQL**: Enable `ssl = on` in `postgresql.conf` with server certificates

<Callout type="info">
Internal TLS is optional for single-node deployments where all pods share the same host. For multi-node clusters, TLS between nodes is strongly recommended.
</Callout>

## Secrets Management

### Credential Rotation

Rotate credentials regularly:

| Secret | Rotation Method | Recommended Interval |
|--------|----------------|---------------------|
| PostgreSQL passwords | Update `.env`, restart pod-database and dependents | 90 days |
| OpenBao AppRole secret_id | Re-run `make bootstrap-secrets` | 90 days |
| SEAL signing keys | Regenerate with `make generate-keys`, restart pod-core | Annually |
| GHCR token | Regenerate GitHub PAT, update `.env` | Annually |
| LLM API keys | Rotate via provider dashboard, update `.env` or OpenBao | Per provider policy |

### Avoiding Plaintext Secrets

- Never commit `.env` files to version control
- Use `env:VAR_NAME` or `secret:path` credential prefixes in `aegis-config.yaml`
- Store sensitive values in OpenBao and reference them via the `secret:` prefix

## Resource Limits

Configure container resource limits in pod YAML definitions to prevent resource exhaustion:

```yaml
resources:
  limits:
    memory: "4Gi"
    cpu: "2000m"
  requests:
    memory: "1Gi"
    cpu: "500m"
```

Recommended minimum limits per pod:

| Pod | CPU Request | Memory Request | CPU Limit | Memory Limit |
|-----|------------|---------------|-----------|-------------|
| pod-core | 1000m | 2Gi | 4000m | 8Gi |
| pod-database | 500m | 1Gi | 2000m | 4Gi |
| pod-temporal | 500m | 1Gi | 2000m | 4Gi |
| pod-observability | 500m | 2Gi | 2000m | 8Gi |
| pod-storage | 250m | 512Mi | 1000m | 2Gi |
| pod-secrets | 100m | 128Mi | 500m | 512Mi |
| pod-seal-gateway | 250m | 256Mi | 1000m | 1Gi |

## Network Segmentation

### Firewall Rules

Only the Caddy edge proxy should be exposed publicly:

| Port | Protocol | Exposure | Purpose |
|------|----------|----------|---------|
| 80 | TCP | Public | HTTP redirect to HTTPS |
| 443 | TCP | Public | HTTPS (Caddy) |
| All others | TCP | Internal only | Inter-pod communication |

### Podman Network

Platform pods run on the `aegis-network` bridge. Agent execution containers run on a separate `aegis-exec-network` bridge, isolated from the platform network. This separation exists because Podman's netavark network driver corrupts outbound NAT routing for existing pods when containers are frequently created and destroyed on the same network. By placing agent containers on their own network, platform pod routing remains stable regardless of agent execution churn. Agent containers reach the orchestrator at the address and port of `AEGIS_ORCHESTRATOR_URL`, which in the reference deployment is `http://<host-internal-ip>:8088`.

**In the reference deployment ([aegis-platform-deployment](https://github.com/100monkeys-ai/aegis-platform-deployment)), a container on the agent network reaches the orchestrator and nothing else.** It can open a TCP connection to the address and port of `AEGIS_ORCHESTRATOR_URL`, the orchestrator's dispatch endpoint, and to no other destination: not the link-local range (a cloud provider's metadata server), not the host's own addresses or other published ports, not the platform network and its pods, not another agent container, not the internet. `podman/networks/isolate-agent-network.sh` writes the rule, and the README's section "Networks, and the agent network's rule" describes it. The script accepts only an `AEGIS_ORCHESTRATOR_URL` of the form `http://<IPv4 address>:<port>`, and it runs again on every deploy and redeploy, because rootless Podman makes its network namespace, and the rules in it, anew after the user's last container stops.

Traffic between two containers on the same bridge is filtered only when the host has the `br_netfilter` kernel module loaded, which takes root (`modprobe br_netfilter`); without it, one agent container can reach another.

**What an agent author meets:** any command run in an agent's container (`cmd.run`, a ContainerRun step) that needs a host other than the orchestrator, such as `pip install`, `npm install`, `git clone` or `curl` of a URL, fails after its connection times out. Web access goes through the orchestrator's own tools (`web.fetch`, `web.search`), which run in the orchestrator, not in the container, and images are pulled by Podman, not by the container.

For multi-node deployments, use the cluster protocol (port 50056) with mTLS between nodes. See [Multi-Node Deployment](/docs/deployment/multi-node).

## Access Control

### Grafana Access

By default, Grafana allows anonymous viewer access. For production:

1. Disable anonymous access in Grafana configuration
2. Set up role-based access control for dashboards

### OpenBao Access

- The OpenBao UI should not be exposed publicly (remove the `secrets.*` Caddy route)
- Use AppRole authentication exclusively; avoid root tokens in production
- Enable audit logging

## Image Security

### Scanning

Scan container images for vulnerabilities before deployment:

```bash
# Using Trivy
trivy image ghcr.io/100monkeys-ai/aegis-runtime:1.2.3
trivy image ghcr.io/100monkeys-ai/aegis-temporal-worker:1.2.3
trivy image ghcr.io/100monkeys-ai/aegis-seal-gateway:1.2.3
```

### Pinned Versions

Always use pinned semver tags in production, never `:latest`:

```bash
# In .env
AEGIS_IMAGE_TAG=1.2.3
```

## Monitoring & Alerting

Verify that all Prometheus alert rules are active:

```bash
# Check alert rules via Prometheus API
curl http://localhost:9090/api/v1/rules | jq '.data.groups[].rules[].name'
```

Configure alert routing in Prometheus Alertmanager for your notification channels (PagerDuty, Slack, email).
