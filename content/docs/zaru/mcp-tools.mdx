Zaru exposes the AEGIS platform to MCP clients through a set of tools organized by conversation mode. The mode you select at the start of a conversation determines which tools are active. This page covers each mode's tool set with purpose, key parameters, and example calls.

For complete input/output schemas, see the [MCP Tool Reference](/docs/reference/mcp-tool-reference). For client connection instructions, see [Connect Zaru to Any MCP Client](/docs/zaru/mcp-client-setup).

---

## How Modes Control Tool Access

Every Zaru conversation runs in one of five modes. Modes filter the tool surface exposed to the AI assistant — the underlying platform tools do not change, but the assistant can only call what the mode makes available.

| Mode          | Tools available                                   | Purpose                                          |
| ------------- | ------------------------------------------------- | ------------------------------------------------ |
| **chat**      | `zaru.*` only                                     | Conversation and planning; no platform execution |
| **agentic**   | `zaru.*` + agent/task tools                       | Discover and run existing agents                 |
| **execute**   | `zaru.*` + execute pipeline tools                 | One-shot code execution from natural language    |
| **architect** | `zaru.*` + workflow/agent design tools            | Design and deploy agents and workflows           |
| **operator**  | All tools                                         | Full platform access, no filtering; only under an [operator escalation](#operator-escalation) |

To initialize in a specific mode:

```text
zaru init agentic
```

To switch modes mid-session, tell the assistant to switch — it calls `zaru.mode` and the tool set updates immediately.

<Callout type="info">
  Outside of Zaru — in agent inner loops and via direct API calls — tools are
  not mode-filtered. Mode filtering is a Zaru-client concern. Inside a running
  agent container, every built-in tool is available subject to the agent's
  security context and `spec.tools` allowlist.
</Callout>

## Client Capabilities and Mode Gating

Some Zaru affordances are surfaced via **client capabilities** declared at session start. The Zaru web client declares `live`, `vibecode`, and `chat-uploads`. External MCP clients do not declare any of these.

The `chat-uploads` capability gates the chat input's file-upload UI (paperclip icon, drag-and-drop, paste). It is bound to `agentic` and `workflow` modes only — in those modes the upload affordance appears, the system prompt teaches the model how attachments flow through dispatches, and tool calls to `aegis.task.execute`, `aegis.agent.generate`, and `aegis.execute.intent` may carry an `attachments` array.

Other modes (`chat`, `execute`, `live`, `vibecode`, operator) do not surface the upload affordance, even when the capability is declared. External clients that do not declare `chat-uploads` see no attachment guidance and the platform rejects out-of-band attachment payloads as a defense-in-depth check.

See [File Uploads in Chat](/docs/zaru/chat#file-uploads-in-chat) for the user-facing flow.

## Connections and Profiles

A connection may send the `x-zaru-contexts` header to choose, for every request, which of the person's connections the tools use: for each tool server a binding id, a list of binding ids, or `null` for none; or, alone, `{"@profile": "<profile id>"}` to choose one of the person's [profiles](/docs/zaru/profiles). With a profile, the tools offered are the profile's, every forwarded call carries it, and `zaru.init` and `zaru.mode` teach the model the profile's name, its Nuclear Notes workspace and its instructions. A header of any other shape is answered `400`.

## Waiting on Long Executions

An MCP client gives up on a tool call after about a minute, so on Zaru's MCP server (`https://mcp.myzaru.com/mcp/v1`) one call to a wait tool (`aegis.agent.wait`, `aegis.task.wait`, `aegis.execute.wait`, `aegis.workflow.wait`) waits at most **45 seconds**. A `timeout_seconds` that is a whole number from 0 to 45 is used as given; a larger value, a fractional value or none waits 45 seconds. Each wait tool's description says so.

When the execution finishes within the wait, the result is the execution's final status and output. When it is still running, the call returns an ordinary result rather than an error:

```json
{
  "tool": "aegis.task.wait",
  "execution_id": "e1f2a3b4-...",
  "status": "running",
  "iteration_count": 2,
  "still_running": true,
  "timed_out": true,
  "waited_seconds": 45,
  "message": "Execution e1f2a3b4-... is still running after 45s, iteration count 2. Repeat this same aegis.task.wait call to continue waiting."
}
```

A workflow's result carries `current_state` in place of `iteration_count`. To keep waiting, repeat the same call.

## When AEGIS Refuses a Tool Call

Zaru's MCP server forwards the `aegis.*` tools to AEGIS. When AEGIS refuses such a call or cannot complete it, the client gets an ordinary tool result with `isError: true`, not a JSON-RPC error. The result has one text item holding a JSON object:

```json
{
  "error": {
    "code": "INVALID_ARGUMENTS",
    "message": "Invalid tool arguments: required field 'execution_id' is missing or null for tool 'aegis.task.status'"
  },
  "request_id": "3f9c2a71-5b8e-4d0a-9c1e-7a2b6d4e8f10"
}
```

| Field                 | Meaning |
| --------------------- | ------- |
| `error.code`          | AEGIS's code for the refusal, from [Refusals and Errors](/docs/reference/builtin-tools#refusals-and-errors), or `invoke_failed` (below). |
| `error.message`       | For a refusal of your call, AEGIS's own message: what was refused and why. For `INTERNAL_ERROR`, `UPSTREAM_UNAVAILABLE` and `SERVICE_UNAVAILABLE`, the fixed sentence of that table, never the failure's detail. |
| `request_id`          | AEGIS's id for the refused call. Quote it when you report the failure: it lets an operator find what happened. |
| `retry_after_seconds` | Present when AEGIS said how long to wait, on `RATE_LIMIT_EXCEEDED` and on `UPSTREAM_UNAVAILABLE`: the seconds to wait before calling again. |

The server does not repeat a refused call, apart from the session renewal below. A policy refusal is deterministic: the same call gets the same answer, so change the call instead of repeating it.

**The session is renewed by the server.** The server keeps a SEAL session with AEGIS for each user. When AEGIS answers `401`, meaning the session or the envelope is no longer valid, the server attests again and sends the call once more. If AEGIS answers the second call `401` as well, the result carries AEGIS's code with the message "The session with AEGIS could not be renewed. Try the call again."

**`invoke_failed`.** An answer the server cannot read as one of AEGIS's refusals comes back with the code `invoke_failed` and the message `AEGIS invoke failed: <HTTP status>`. A session the server could not start comes back as `invoke_failed` with `AEGIS attestation failed: <HTTP status>`.

**Not a tool result.** A call AEGIS does not answer at all, because it timed out or AEGIS could not be reached, still fails as a JSON-RPC error. When the server cannot read AEGIS's tool list, `tools/list` fails as a JSON-RPC error with the message `AEGIS tool discovery failed: <HTTP status>`.

The errors of the tools the server handles itself (`zaru.chat`, `zaru.operator.escalate`, `zaru.operator.release`) are listed with each tool below.

## Zaru Client Tools — All Modes

These tools are available in every mode, including chat. They are handled by the Zaru MCP server and never forwarded to the AEGIS orchestrator.

### `zaru.init`

Bootstraps the session. Returns the current mode, system prompt, available tools, and server version. Call this at the start of any MCP session.

| Parameter | Required | Default | Description                                                             |
| --------- | -------- | ------- | ----------------------------------------------------------------------- |
| `mode`    | No       | `chat`  | Mode to activate: `chat`, `agentic`, `execute`, `architect`, or `operator` while the connection holds an [operator escalation](#operator-escalation) |

```json
// zaru.init
{ "mode": "agentic" }
```

### `zaru.mode`

Switches the active conversation mode. In the Zaru web client, this renders an inline confirmation card — the user accepts or declines. In headless MCP clients the switch applies immediately.

| Parameter     | Required | Default | Description                                      |
| ------------- | -------- | ------- | ------------------------------------------------ |
| `target_mode` | Yes      | —       | Mode to switch to                                |
| `reason`      | Yes      | —       | One sentence explaining why the switch is needed |

```json
// zaru.mode
{
  "target_mode": "architect",
  "reason": "Designing a new multi-step workflow requires architect tools."
}
```

### `zaru.docs`

Searches AEGIS and Zaru documentation at `docs.100monkeys.ai`. Results are cached for 5 minutes per query.

| Parameter | Required | Default | Description              |
| --------- | -------- | ------- | ------------------------ |
| `query`   | Yes      | —       | What you want to look up |

```json
// zaru.docs
{ "query": "how to configure a persistent volume for execute mode" }
```

### `zaru.memory.get`

Reads the caller's persistent memory — a per-user markdown blob shared across every MCP client connected as that user (Zaru Web, Claude Desktop, Windsurf, etc.). The current memory is auto-injected into the system prompt at session start, so calling this mid-conversation is mostly used to obtain the current `version` before a `zaru.memory.set`, or to re-read after a conflict.

_No parameters — accepts an empty object `{}`._

```json
// zaru.memory.get
{}
```

```json
// response
{
  "content": "# User memory\n\n- Prefers concise answers...",
  "version": 7,
  "updated_at": "2026-04-28T14:32:11Z"
}
```

When no memory has been written yet, returns `{ "content": "", "version": 0, ... }`.

### `zaru.memory.set`

Persists a new memory state. Pass the **full** new markdown blob — not a diff or patch — together with the `version` returned by the most recent `zaru.memory.get`. The server increments the version on success.

Use this to record user preferences, work-style cues, recurring projects, frustrations, or anything worth carrying into future conversations. Always call `zaru.memory.get` first to obtain the current `version`. Keep memory concise and signal-rich — it is not a transcript log.

| Parameter | Required | Description                                              |
| --------- | -------- | -------------------------------------------------------- |
| `content` | Yes      | Full new memory markdown blob (not a diff)               |
| `version` | Yes      | Version returned by the previous `zaru.memory.get` call  |

```json
// zaru.memory.set
{
  "content": "# User memory\n\n- Prefers concise answers...\n- New project: zaru-edge",
  "version": 7
}
```

If `version` does not match the server's current version, the call returns a structured conflict error containing the server's current `{ content, version, updated_at }`. Merge the intended changes into that content and retry with the new version.

### `zaru.schedule`

Proposes a schedule to the person: one of their agents or workflows run later, once or again and again. It creates nothing. Zaru Web shows the proposal as a **Schedule this?** card that names what it runs and when, and the turn ends there; **Schedule** opens the schedule form filled in from the proposal, **Not now** closes it. See [Schedules](/docs/workflows/schedules).

| Parameter     | Required | Description |
| ------------- | -------- | ----------- |
| `target_kind` | Yes      | `agent` or `workflow` |
| `target`      | Yes      | The name or id of one of the person's agents or workflows. It must already exist. |
| `intent`      | Yes      | What each run is for, in the person's words |
| `input`       | Yes      | An object of the target's input values, or one string, carried as `{"prompt": <the string>}` |
| `at`          | One of   | For one run: an RFC 3339 time at least one minute from now and at most a year ahead |
| `recurrence`  | One of   | For a repeating run: `cron` (five fields, required), `timezone` (default `UTC`) and `jitter_seconds` (0 to 3600, default 0); at most once every 5 minutes |
| `reason`      | Yes      | One plain sentence, shown to the person, saying what the schedule will do for them |

Give exactly one of `at` or `recurrence`. After the shape is checked, the server reads the person's own agent or workflow list and accepts a `target` equal to an entry's name or id. Otherwise the proposal is refused, with no card:

- an empty `target`: "'target' must name one of your agents or workflows. Find or make the one that does this, run it once, then propose the schedule naming it."
- no such agent or workflow: "You have no agent named '&lt;target&gt;'. Find or make the one that does this, run it once, then propose the schedule naming it." (or "workflow")
- the list could not be read: "Your agents and workflows could not be read just now, so nothing was proposed."

In chat mode the companion proposes a schedule only for an agent or workflow the conversation has already named or run; otherwise it offers agentic mode with `zaru.mode`, where the one that does it is found or made and run once, and the proposal follows that run. In agentic and workflow modes it names as the target the agent or workflow it ran. In no mode does it make a schedule itself.

```json
// zaru.schedule
{
  "target_kind": "agent",
  "target": "mail-reply-watcher-agent",
  "intent": "Watch for a reply from Cloudflare about the startup program and tell me when it comes",
  "input": "Look for a reply from Cloudflare about the startup program",
  "recurrence": { "cron": "0 */6 * * *", "timezone": "America/Los_Angeles", "jitter_seconds": 300 },
  "reason": "Checks your inbox every 6 hours and tells you the moment a reply arrives."
}
```

### `zaru.conversations.list`, `zaru.conversations.read`, `zaru.conversations.search`

Read the person's own Zaru conversations: the ones held on the Zaru Web chat page and the ones held through `zaru.chat`. They read nothing of anyone else's, whatever tenant was active, and wait for no approval.

| Tool | Parameters | Returns |
| ---- | ---------- | ------- |
| `zaru.conversations.list` | `limit` (1 to 50, default 20) | `{ conversations: [{ id, title, mode, updated_at, message_count, archived, current }], more }`, newest first by the last message |
| `zaru.conversations.read` | `conversation_id` (required), `cursor`, `page_size` (1 to 100, default 50) | `{ conversation: { id, title, mode, updated_at }, messages, next_cursor }`, oldest first |
| `zaru.conversations.search` | `query` (3 to 200 characters, required), `limit` (1 to 50, default 20) | `{ hits: [{ conversation_id, title, message_id, role, created_at, snippet, current }], more }`, newest first |

A message `read` returns is `{ id, role, text, created_at }` for something the person or Zaru said, with `channel: "api"` on a message the person sent through another app and `truncated: true` on a text cut at 4,000 characters; or `{ id, role: "tool_call", tool, outcome, created_at }` for a tool call, `outcome` being `ok`, `error` or `aborted`. Tool arguments and results are not returned. Pass `next_cursor` as `cursor` to read the next page; it is `null` at the end. `search` matches the whole query literally, without regard to case, in titles and in what the person and Zaru said; `message_id` is `null` for a match in a title, and `snippet` is up to 200 characters around the match.

`current` marks the conversation the call is made in. Reading it is refused with `current_conversation`: "That is the conversation we are in; it is already in front of you." A refusal is a tool error whose text is `{ "error": <code>, "message": <sentence> }`, the code one of `unauthorized`, `conversation_not_found`, `current_conversation`, `invalid_request` or `unavailable`; another person's conversation is `conversation_not_found`, exactly as one that does not exist.

```json
// zaru.conversations.search
{ "query": "Google credits", "limit": 5 }
```

## Talking to Zaru from Another Client

### `zaru.chat`

Runs one turn of the Zaru companion on Zaru's own model, in one of your stored Zaru Web conversations, and returns its answer. The turn is the one the chat page at ask.myzaru.com runs, with the companion's prompt, your memory and the tools of the mode, and the conversation is stored with your others: it is listed on the page and can be continued there or through the tool.

Zaru's MCP server lists `zaru.chat` to every client that connects to it, and handles it itself, never forwarding it to the AEGIS orchestrator. It is not one of the companion's own tools: no mode offers it inside a Zaru turn, and a call made from inside a turn is refused with `mode_not_available`, so a turn never starts another turn.

The turn runs as the user the MCP connection is authenticated as, by an `aegis_` API key or a Zaru sign-in.

| Parameter         | Required | Default                                                   | Description                                                            |
| ----------------- | -------- | --------------------------------------------------------- | ---------------------------------------------------------------------- |
| `message`         | Yes      | —                                                         | Your message for this turn, 1 to 32,768 characters                     |
| `conversation_id` | No       | a new conversation                                        | UUID of a conversation of yours to continue, begun on the page or here |
| `mode`            | No       | the conversation's stored mode, or `chat` for a new one   | `chat`, `agentic`, `workflow` or `execute`, or `operator` while the connection's key holds an [operator escalation](#operator-escalation); a different mode changes the conversation's mode |

```json
// zaru.chat
{
  "message": "Summarise what we decided about the release yesterday.",
  "conversation_id": "<conversation-uuid>"
}
```

The result is a JSON object, returned as text and as structured content:

| Field                   | Description                                                                                                                       |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `conversation_id`       | The conversation the turn ran in; for a new conversation, its new id                                                              |
| `status`                | `complete`, or `incomplete` when the turn reached its time limit                                                                  |
| `answer`                | The companion's answer                                                                                                            |
| `tool_calls`            | Each tool call of the turn as `{ name, arguments, outcome, result, result_truncated }`; `outcome` is `ok` or `error`, and `result` is cut to 8,192 characters, with `result_truncated` saying whether it was |
| `model`, `mode`         | The model and the mode the turn ran on                                                                                            |
| `mode_switch_requested` | Present when the companion asked to switch modes, as `{ mode, reason }`; the switch is not applied                                |
| `usage`                 | Present when the model reported it: `{ prompt_tokens, completion_tokens, total_tokens }`                                          |
| `goal`                  | Present when the turn holds a goal: `{ goal_id, statement, state, rounds, verdicts }`, each verdict `{ round, score, confidence, outcome, reasoning }` with `round` the round it judged, counted from 0. A goal handed on to be judged after the call reads `state` `open` |

**Limits.** One call runs one turn of at most five model calls. No model call starts later than 40 seconds after the request arrives, and the turn ends at 50 seconds, so a call answers within the minute an MCP client waits. A turn that reaches the limit ends `incomplete` with what it did so far stored. In `agentic` mode a turn that starts creating or running an agent sets a goal ([Goals in Agentic Mode](/docs/zaru/chat#goals-in-agentic-mode)): Zaru judges it after the call has answered and continues by itself, without your next message, until it is met, cannot be met or its bounds end it. Otherwise, to continue, send your next message in the same conversation. A connection authenticated by a Zaru sign-in instead of an `aegis_` API key gets no goal. The companion sees the most recent 100 of the conversation's messages.

**Knowing the work is done.** `status` says only whether the turn reached its time limit: a turn that started work can be `complete` while that work goes on. Whether the request is done is the goal's `state`: `open` while it is judged or continued, then `met`, `cannot_be_met`, `exhausted` (no round left), `expired` (open past its lifetime) or `superseded` (a later message started new work). Read it with [`aegis.goal.status`](/docs/reference/mcp-tool-reference#aegisgoalstatus) and the answer's `goal_id` where the connection lists that tool; the conversation on the page shows the same verdicts as cards.

**Errors.** A refusal is a tool error whose text is a JSON object `{ "error", "message" }`. The `error` is one of:

| `error`                   | When                                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------- |
| `unauthorized`            | The connection's API key or session is not valid                                             |
| `invalid_request`         | The arguments are not valid: `message` empty or too long, `conversation_id` not a UUID, or `mode` not a Zaru mode |
| `conversation_not_found`  | No conversation of yours has that id                                                         |
| `conversation_archived`   | The conversation is archived                                                                 |
| `active_execution_exists` | A turn, or a goal's continuation round, is already running in that conversation              |
| `mode_not_available`      | `mode` is `live` or `vibecode`, or `operator` without an operator escalation, or the call was made from inside a Zaru turn |
| `inference_unavailable`   | Zaru cannot reach its model; try again in a moment                                           |
| `turn_failed`             | The turn could not be run, or failed after it started; a turn that failed after it started keeps what it did stored |

## Operator Escalation

Through Zaru's MCP server, operator mode and the operator tools are reached only by an operator escalation: an operator generates a one-time code on Zaru Web, gives it to the AI agent, and the agent presents it. Until then a connection carries the ordinary tools of its user, whatever that user's platform role, and an `aegis-system` token presented to the server is refused `401`.

**Who can escalate.** A person with the `aegis:admin` or `aegis:operator` role; `aegis:readonly` generates no code. The code is redeemed by an `aegis_` API key the same person created from their ordinary Zaru sign-in ([API Keys](/docs/zaru/api-keys)). A key created in an operator session, which carries the role itself, cannot hold an escalation, and a connection authenticated by a Zaru sign-in instead of an API key cannot escalate.

**Steps.**

1. In Zaru Web's admin area, open **MCP escalation** and click **Generate code**. The page shows six digits once, with the time left to use them; they are not shown again.
2. Give the six digits to the agent. It calls `zaru.operator.escalate` with them.
3. The agent lists its tools again: the connection now carries the operator tools and `operator` mode.

The page also lists your active escalations by key, role, start and expiry, each with **End now**.

### `zaru.operator.escalate`

Listed to every client connected with an `aegis_` API key and handled by Zaru's MCP server, which presents the code to AEGIS with the connection's own key.

| Parameter | Required | Description |
| --------- | -------- | ----------- |
| `code`    | Yes      | The six digits shown on the **MCP escalation** page, exactly as given |

```json
// zaru.operator.escalate — 123456 is an example, not a code
{ "code": "123456" }
```

Returns `{ aegis_role, expires_at }`: the role, `aegis:admin` or `aegis:operator`, and when the escalation ends. A refusal is a tool error whose text is `{ "error", "message" }`:

| `error`                       | When |
| ----------------------------- | ---- |
| `invalid_code`                | The code is not six digits, matches no live code of the key's user (already used, invalidated or wrong), or the key cannot hold an escalation |
| `code_expired`                | The code matched after its validity ended |
| `escalation_requires_api_key` | The connection is not authenticated by an `aegis_` API key |
| `orchestrator_unavailable`    | Zaru's MCP server could not reach AEGIS or got no usable answer |

A code that is not six digits is refused by the server and never sent. Any other wrong code counts against every live code of that person, and the fifth failure invalidates them: an agent asks the person for the code and never guesses one.

### `zaru.operator.release`

Listed only while the connection's key holds an escalation. No parameters. Ends the escalation now and returns `{ ended_at }`; refused `escalation_not_found` when the key holds none, and `orchestrator_unavailable` as above.

### What an Escalation Lasts and Carries

- A code is valid once, for 5 minutes after it is generated by default; an escalation lasts 30 minutes from its redemption by default. A deployment sets both, and the failure count, in `spec.iam.operator_escalation` ([Node Configuration](/docs/reference/node-config#speciam)).
- The escalation is held by the one API key that redeemed it. It ends at its expiry, at **End now** on the page, at `zaru.operator.release`, when the key is revoked, when an administrator ends every escalation of that operator, or when the operator's role is withdrawn.
- While it lasts, the connection's tool list is the operator surface, and `zaru.init` and `zaru.mode` offer `operator` mode. `aegis.task.list` without `agent_id` lists the most recent executions of every tenant, each with its `tenant_id`, and `aegis.task.status`, `aegis.task.logs` and `aegis.workflow.logs` read an execution of any tenant by its id. Naming another tenant in a tool's `tenant_id` argument is admitted for `aegis:admin` only.
- A tool call that arrives after the end is refused, and the ordinary tools return at the next tool listing.
- AEGIS reads the operator's role again from the identity provider at every escalated tool call and at every redemption. Once the role is withdrawn or changed, or the account is disabled or removed, the next escalated call is refused and every escalation of that operator ends; an escalation that makes no call ends within a minute. A code redeemed after that is refused `invalid_code`. While the identity provider cannot be read, escalated calls and redemptions are refused and the escalation stays active until the role can be read again or the escalation expires.
- Every tool call made under an escalation is recorded in the platform's admin audit log under the operator's identity, with the tenant it acted on. On the Podman deployment, `make operator-escalation-audit` prints these rows ([Makefile Targets](/docs/deployment/podman#makefile-targets)).
- Neither tool is offered to the companion inside a Zaru Web turn: only the person holding the code begins or ends an escalation.

## Agentic Mode Tools

Agentic mode gives the assistant access to agent discovery, generation, task execution, and monitoring. Use it when you want to run existing agents or generate new ones from a description.

In agentic mode the companion's prompt sends every request for a result to an agent, however simple, starting with `aegis.agent.list`; it does not answer such a request itself, even with an answer it already knows. It answers directly only talk about the work in hand (what is running, what a result means, what it will do next), and offers Chat through `zaru.mode` for conversation alone.

In agentic mode the companion's prompt has it treat a system message headed **Goal check** as coming from Zaru, not from you: the message names the executions already started for your goal and what the judge found missing, and the companion continues from them, reading a completed execution's result with `aegis.task.wait` or `aegis.execution.file` instead of starting it again. Zaru Web sends this message at the start of a continuation round and of a turn that begins while the conversation's goal is open ([Goals in Agentic Mode](/docs/zaru/chat#goals-in-agentic-mode)).

### Agent Discovery and Generation

**`aegis.agent.list`** — Lists all deployed agents with name, version, status, and description. No parameters required. Use this to find agents before running them.

```json
// aegis.agent.list
{}
```

**`aegis.agent.generate`** — Starts an async authoring loop that generates a complete agent manifest from a plain-English description and deploys it. Returns an `execution_id` immediately.

| Parameter | Required | Description                                              |
| --------- | -------- | -------------------------------------------------------- |
| `input`   | Yes      | Natural-language description of what the agent should do |

```json
// aegis.agent.generate
{
  "input": "An agent that reads a CSV file from /workspace, computes summary statistics for each numeric column, and writes a markdown report to /workspace/report.md"
}
```

```json
// response
{ "execution_id": "e1f2a3b4-...", "status": "started" }
```

Follow with `aegis.agent.wait` to block until generation completes.

**`aegis.agent.wait`** — Blocks until an agent generation (or any agent execution) reaches a terminal state.

| Parameter               | Required | Default | Description                                                   |
| ----------------------- | -------- | ------- | ------------------------------------------------------------- |
| `execution_id`          | Yes      | —       | ID returned by `aegis.agent.generate` or `aegis.task.execute` |
| `poll_interval_seconds` | No       | 10      | Seconds between internal polls                                |
| `timeout_seconds`       | No       | 45      | Seconds this call waits, at most 45 ([Waiting on Long Executions](#waiting-on-long-executions)) |

```json
// aegis.agent.wait
```

## Execute Mode Tools

Execute mode provides a single-shot pipeline: describe a computation in plain English, optionally supply typed inputs, and Zaru generates and runs the code in a sandboxed container. No pre-existing agent is required.

For the full user guide including tier limits, supported languages, and workspace options, see [Running Code with Execute Mode](/docs/zaru/execute-mode).

### `aegis.execute.intent`

Starts the intent-to-execution pipeline. Discovers or generates a code-writing agent, produces the code, runs it in an isolated container, and returns the result.

| Parameter         | Required | Default   | Description                                                      |
| ----------------- | -------- | --------- | ---------------------------------------------------------------- |
| `intent`          | Yes      | —         | Natural-language description of what to compute                  |
| `inputs`          | No       | —         | Typed scalar or structured inputs embedded in the generated code |
| `language`        | No       | `python`  | `python`, `javascript`, or `bash`                                |
| `volume_id`       | No       | ephemeral | Persistent volume ID for result storage (Pro and higher)         |
| `timeout_seconds` | No       | —         | Execution timeout override                                       |

```json
// aegis.execute.intent
{
  "intent": "compute the mean, median, and standard deviation of this list of numbers",
  "inputs": { "numbers": [14, 22, 8, 31, 19, 7, 45] },
  "language": "python"
}
```

Returns a `pipeline_execution_id`. Use `aegis.execute.wait` to block until the pipeline finishes.

### `aegis.execute.status`

Returns the current status of a pipeline run.

| Parameter               | Required | Description                           |
| ----------------------- | -------- | ------------------------------------- |
| `pipeline_execution_id` | Yes      | ID returned by `aegis.execute.intent` |

```json
// aegis.execute.status
{ "pipeline_execution_id": "p1b2c3d4-..." }
```

Returns `{ "status": "running" }` while in progress, or a completed result with `final_result` and `duration_ms`.

### `aegis.execute.wait`

Blocks until the pipeline execution completes. Pass the `pipeline_execution_id` as `execution_id`.

| Parameter               | Required | Default | Description                                             |
| ----------------------- | -------- | ------- | ------------------------------------------------------- |
| `execution_id`          | Yes      | —       | The `pipeline_execution_id` from `aegis.execute.intent` |
| `poll_interval_seconds` | No       | 5       | Seconds between polls                                   |
| `timeout_seconds`       | No       | 45      | Seconds this call waits, at most 45 ([Waiting on Long Executions](#waiting-on-long-executions)) |

```json
// aegis.execute.wait
{ "execution_id": "p1b2c3d4-...", "timeout_seconds": 45 }
```

### `aegis.workflow.wait`

Also available in execute mode for waiting on workflow executions started by the pipeline internally. Same parameters as `aegis.execute.wait`.

## Architect Mode Tools

| Parameter | Required | Description                                       |
| --------- | -------- | ------------------------------------------------- |
| `key`     | Yes      | `"agent/manifest/v1"` or `"workflow/manifest/v1"` |

## Operator Mode Tools

Operator mode exposes all tools with no filtering. It includes everything from the modes above plus the tool groups below.

<Callout type="info">
  Through Zaru's MCP server, operator mode is reached only by an [operator
  escalation](#operator-escalation); a platform admin realm token is refused. System
  tools (`aegis.agent.create`, `aegis.agent.update`, `aegis.workflow.create`,
  `aegis.workflow.update`, `aegis.workflow.promote`, `aegis.workflow.demote`)
  require operator credentials. Destructive tools (`aegis.agent.delete`,
  `aegis.workflow.delete`, `aegis.task.remove`, `aegis.workflow.remove`,
  `aegis.system.*`) are similarly restricted to operator sessions.
</Callout>

### Agent and Workflow Lifecycle

These tools manage the registry directly. They take a manifest YAML and register it synchronously — no async generation loop.

**`aegis.agent.create`** / **`aegis.agent.update`** — Deploy or update an agent manifest. Pass `force: true` to overwrite an existing name/version pair.


<Callout type="warn">
  `aegis.agent.delete` is irreversible. In-progress executions continue to
  completion but new tasks cannot be dispatched against the deleted agent.
</Callout>

```json
// aegis.agent.delete
{ "agent_id": "a1b2c3d4-..." }
```

**`aegis.agent.search`** — Semantic search over deployed agents by natural-language query.

```json

  "limit": 5,

}
```

**`aegis.workflow.create`** / **`aegis.workflow.update`** — Register or update a workflow manifest.

```json
// aegis.workflow.create

}
```

**`aegis.workflow.validate`** — Validates a workflow manifest without registering it.

```json
// aegis.workflow.validate
{ "manifest_yaml": "apiVersion: aegis.ai/v1\nkind: Workflow\n..." }
```

**`aegis.workflow.export`** — Retrieves the raw manifest YAML of a registered workflow by name.

**`aegis.workflow.delete`** — Permanently removes a workflow from the registry.

<Callout type="warn">
  `aegis.workflow.delete` removes the definition. In-progress executions are not
  terminated, but new executions of this workflow will no longer be possible.
</Callout>

**`aegis.workflow.run`** — Executes a registered workflow by name.

| Parameter | Required | Default | Description                        |
| --------- | -------- | ------- | ---------------------------------- |
| `name`    | Yes      | —       | Workflow name                      |

**`aegis.workflow.search`** — Semantic search over registered workflows.

```json
// aegis.workflow.search
```

## Edge Fleet Tools (System Tier)

Three system-tier MCP tools cover edge fleet operations. They are gated by an operator/tenant-admin SecurityContext and surfaced to operator-mode conversations and the Fleet Launcher UI.

### `aegis.edge.fleet.invoke`

Invoke any registered tool against an `EdgeTarget` with a `FleetDispatchPolicy`. Per-node `CommandProgress` chunks stream back tagged with `node_id`; the terminal payload is `FleetExecutionResult { fleet_command_id, targets_resolved, targets_skipped, per_node, summary }`.

**Inputs (selected fields):**

| Field                             | Description                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------------- |
| `target`                          | Tagged-union over `Node`, `Group`, `Selector`, `All`.                                             |
| `tool`                            | Tool name to invoke per node. Must declare `fleet_capable: true` to accept multi-target dispatch. |
| `args`                            | Tool-specific argument map.                                                                       |
| `policy.mode`                     | `Sequential` / `Parallel` / `Rolling { batch }`.                                                  |
| `policy.failure_policy`           | `FailFast` / `ContinueOnError` / `StopAfter(N)`.                                                  |
| `policy.max_concurrency`          | Optional cap.                                                                                     |
| `policy.require_min_targets`      | Refuse upfront if fewer matches resolve.                                                          |
| `policy.per_target_deadline_secs` | Per-call deadline propagated as `EdgeCommand.deadline`.                                           |

### `aegis.edge.fleet.list`

Resolve an `EdgeTarget` to a node list **without dispatching**. The operationally critical answer to "show me which hosts this selector hits before I run anything." Zaru's selector preview panel is built on this tool.

### `aegis.edge.fleet.cancel`

Broadcast `Cancel` to every in-flight per-node command in a fleet operation, addressed by `fleet_command_id`. Already-completed nodes are unaffected.

### `fleet_capable` flag

Tool descriptors carry a `fleet_capable: bool` flag. Tools that are inherently single-target (interactive shells, file uploads where the target host matters semantically) declare `fleet_capable: false` and refuse multi-target dispatch even when the caller tries to fan them out.

For the underlying model, see [fleet operations](/docs/concepts/fleet-operations); for the REST shape, see [edge REST API](/docs/reference/edge-rest-api).
