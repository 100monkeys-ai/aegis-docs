# Edge Fleet Operations

This guide is the operational counterpart to [the fleet operations concept page](/docs/concepts/fleet-operations). Where that page describes the model, this page walks through the actual commands you run, the output you read, and the patterns that work in practice.

By the end you'll know how to:

1. Run an ad-hoc command across many hosts.
2. Roll a configuration change in waves with halt-on-failure.
3. Read streaming per-node results.
4. Cancel a runaway run.
5. Inspect run history.

## Prerequisites

- At least two enrolled edge hosts in your tenant. See [edge host setup](/docs/zaru/edge-host-setup).
- Tags or groups defined for the targeting you want. See [tag and group management](/docs/zaru/edge-tag-and-group-management).
- A user with permission to call the system-tier `aegis.edge.fleet.*` MCP tools (operator or tenant-admin).

## The shape of a fleet run command

```bash
aegis edge fleet run \
  --target <expr> \
  --tool <tool-name> [--arg key=value]... \
  [--mode parallel|sequential|rolling=N] \
  [--max-concurrency N] \
  [--on-error fail-fast|continue|stop-after=N] \
  [--require-min N] \
  [--deadline 60s]
```

Per-node results stream live; when every per-node call has terminated, a final summary is printed.

### `<expr>` — target shorthand

| Form                               | Meaning                              |
| ---------------------------------- | ------------------------------------ |
| `@<node-id>`                       | Single node.                         |
| `group:<name>`                     | Saved group.                         |
| `tags=a,b labels=k=v tools=docker` | Ad-hoc selector.                     |
| `all`                              | Every Connected edge of your tenant. |

## Recipe 1: ad-hoc parallel command

You want to know which kernel every Linux host in your fleet is running. Read-only, idempotent — parallel and continue-on-error are the right defaults.

```bash
aegis edge fleet run \
  --target tags=linux \
  --tool cmd.run --arg cmd="uname -r" \
  --mode parallel \
  --on-error continue \
  --deadline 10s
```

Streamed output (each line tagged with the originating node):

```text
[n-7a3b2f workstation-east] 6.8.0-31-generic
[n-1c8d4e workstation-west] 6.8.0-31-generic
[n-9f2a31 db-mirror-1]      6.5.0-15-generic
[n-4e7c80 db-mirror-2]      6.5.0-15-generic
[n-3b1d9f bastion]          6.1.0-18-amd64

✔ Fleet run a3f4...c8d2 complete
  ok=5  err=0  timed_out=0
```

## Recipe 2: rolling restart with halt-on-first-failure

You want to restart `nginx` across the web tier, in waves of five, and stop immediately if any host reports a failure.

```bash
aegis edge fleet run \
  --target group:web-tier \
  --tool service.restart --arg name=nginx \
  --mode rolling=5 \
  --on-error stop-after=1 \
  --deadline 30s
```

Streamed output:

```text
[wave 1] starting 5 of 12 nodes
  [n-7a3b2f web-east-1]   restarting nginx... ok (exit=0, 1.2s)
  [n-1c8d4e web-east-2]   restarting nginx... ok (exit=0, 1.4s)
  [n-9f2a31 web-east-3]   restarting nginx... ok (exit=0, 1.1s)
  [n-4e7c80 web-east-4]   restarting nginx... ok (exit=0, 1.5s)
  [n-3b1d9f web-east-5]   restarting nginx... ok (exit=0, 1.3s)
[wave 2] starting 5 of 12 nodes
  [n-2a8c14 web-west-1]   restarting nginx... ok (exit=0, 1.2s)
  [n-5e1f93 web-west-2]   restarting nginx... ERR (exit=3, 0.4s) "service file not found"
✖ stop-after threshold reached (1/1); cancelling in-flight, halting waves

✔ Fleet run b8e1...d4a7 halted
  ok=6  err=1  cancelled=2  not_started=3
```

The halt reason and per-node breakdown are explicit. The `cancelled=2` accounts for in-flight calls in wave 2 that were cancelled when the threshold tripped.

## Recipe 3: refuse to dispatch unless N hosts match

For safety-critical operations you may want a hard floor: "if fewer than 3 hosts match, don't run at all."

```bash
aegis edge fleet run \
  --target tags=db,prod \
  --tool cmd.run --arg cmd="systemctl status postgres" \
  --require-min 3
```

If only 2 hosts match, the dispatch is refused upfront and no per-node call is made:

```text
✖ require-min not satisfied: matched 2, required 3
  Resolved nodes:
    n-9f2a31  db-mirror-1   tags=[prod,db]   Connected
    n-4e7c80  db-mirror-2   tags=[prod,db]   Connected
```

## Recipe 4: preview before destructive fan-out

Before running anything destructive, verify the resolved target set:

```bash
aegis edge fleet preview --target tags=prod
```

```text
Resolved 8 nodes (skipped: 1)
  ✓ n-7a3b2f  web-east-1     linux/x86_64  Connected     tags=[prod,web]
  ✓ n-1c8d4e  web-east-2     linux/x86_64  Connected     tags=[prod,web]
  ...
  ⊗ n-9f2a31  db-mirror-1    linux/x86_64  Disconnected  tags=[prod,db]
```

Disconnected hosts are listed under `skipped` with their reason — they're visible to the operator but won't receive the call.

The preview is also available in Zaru's fleet launcher modal as the **Selector Preview Panel** (it counts hosts as you build the selector) and as the system-tier MCP tool `aegis.edge.fleet.list`.

## Recipe 5: cancel a runaway run

If a fleet run is taking too long or you realize it's misconfigured, cancel it by `fleet_command_id`:

```bash
aegis edge fleet cancel a3f4...c8d2
```

The dispatcher broadcasts `Cancel` to every in-flight per-node command. Any wrapped tool that respects context cancellation halts; native external processes get a SIGTERM. Already-completed nodes are unaffected.

The same operation is exposed as the system-tier MCP tool `aegis.edge.fleet.cancel` and as a **Cancel** button in Zaru's live run view.

## Recipe 6: redeploy a binary in waves

You've built a new binary, copied it to a known location on every host, and want to swap it in:

```bash
# Wave 1: validate the new binary on a smoke-test host.
aegis edge fleet run \
  --target @n-smoke-test-host \
  --tool cmd.run --arg cmd="/opt/myapp/bin/new --version" \
  --deadline 5s

# Wave 2: roll across the fleet, 3 at a time, halt on first failure.
aegis edge fleet run \
  --target group:myapp-fleet \
  --tool myapp.swap --arg version=2.4.0 \
  --mode rolling=3 \
  --on-error stop-after=1 \
  --deadline 30s
```

Two-phase rollouts (canary → fleet) become a habit, not a special case.

## Inspecting run history

```bash
aegis edge fleet runs --output table
```

```text
ID         STARTED                TOOL              TARGET            MODE       STATUS    ok/err/skipped
a3f4...c8  2026-04-28 14:32:11Z   service.restart   group:web-tier    rolling=5  halted    6/1/3
b8e1...d4  2026-04-28 11:08:43Z   cmd.run           tags=linux        parallel   complete  12/0/0
```

In Zaru, **Vault → Edge Hosts → Fleet Runs** lists every run with the same fields and links into the live (or archived) per-node view.

## Anti-patterns

| ❌ Don't                                                    | ✅ Do                                                                                                      |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `--target all --on-error continue` for state-mutating tools | Use a more specific target, prefer `--on-error fail-fast` or `--on-error stop-after=N`.                    |
| Skip `--require-min` for safety-critical operations         | Set a floor that matches your contract.                                                                    |
| Run destructive fan-outs without preview                    | `aegis edge fleet preview` first; check the resolved set.                                                  |
| Long deadlines on rolling deploys                           | Short per-target deadlines force fast failures and tighter waves.                                          |
| Re-using a single tag for unrelated meanings                | Pick tag axes — see [tag conventions](/docs/zaru/edge-tag-and-group-management#tag-conventions-that-work). |

## Recipe 7: apply host state, checking first

`host.apply` takes a list of resources and converges the host to them. Each resource reads the host first and acts only where it differs, so a second apply changes nothing. With `check: true` it reports each change it would make and changes nothing. The edge's security context must allow `host.apply` (see [Edge Host Setup](/docs/zaru/edge-host-setup)).

```json
{
  "check": true,
  "state": {
    "resources": [
      { "id": "pkg", "kind": "package", "name": "chrony" },
      {
        "id": "conf",
        "kind": "file",
        "path": "/etc/chrony/conf.d/pool.conf",
        "content": "pool time.cloudflare.com iburst\n",
        "mode": "0644"
      },
      {
        "id": "svc",
        "kind": "service",
        "name": "chrony",
        "enabled": true,
        "running": true,
        "watch": ["conf"]
      }
    ]
  }
}
```

Every resource answers `ok`, `changed` or `failed`, with a short diff. The first failure stops the run unless the state sets `continue_on_failure`. A `command` resource is refused unless `creates`, `unless` or `onlyif` makes it idempotent. Run with `check: true` first, read the diffs, then run again without it.

## Recipe 8: keep host state as a resource

A `HostState` is a registered, versioned resource, like an agent or a workflow, so people, workflows and Zaru all apply the same state with the same record. It names the edges it applies to and its resources:

```yaml
apiVersion: 100monkeys.ai/v1
kind: HostState
metadata:
  name: api-host
spec:
  target: { Selector: { tags: [ { Has: api } ] } }
  vars:
    port: "8080"
  secrets:
    db: "api/db#password"
  resources:
    - { id: pkg, kind: package, name: chrony }
    - id: env
      kind: file
      path: /etc/api.env
      mode: "0600"
      content: |
        PORT=((vars.port))
        DB_PASSWORD=((secret.db))
```

- **Registering and running it.** Register it with `POST /v1/host-states`, or the `aegis.host_state.create` tool. Then `plan` it (check mode) or `apply` it, through `POST /v1/host-states/{name}/plan` and `/apply`, or the `aegis.host_state.plan` and `apply` tools. An apply goes to one edge at a time and stops at the first edge that fails.
- **Placeholders.** `((vars.NAME))` and `((secret.NAME))` are filled in when the state is planned or applied. They use `((…))` so that a file's own `{{…}}` templates pass through untouched. A placeholder the state does not declare is refused at registration.
- **Secrets.**

  - **Where they live:** `api/db#password` names the field `password` at `host-states/api/db` in your tenant's own secret store. Store it with `PUT /v1/host-state-secrets/api/db` and a body of `{"fields": {"password": "…"}}`. Values are write-only: a `GET` on the same path answers field names only.
  - **What sees them:** the state itself holds only the secret's name. The value travels to the edge inside the sealed command. Wherever a report or an error echoes a value, it shows `[secret db]` instead.
- **Approval.** An apply changes hosts, so from Zaru or the MCP tools it waits for your approval, unless you have set "always allow" for it. A plan changes nothing and runs at once.

## Recipe 9: deliver with a workflow

A workflow reaches hosts through `Action` states, which run with no model in the loop:

| Action | Arguments | Does |
| --- | --- | --- |
| `host_state_plan` | `name` | Plans a registered `HostState` |
| `host_state_apply` | `name` | Applies it, one edge at a time; waits for the run's person to approve |
| `edge_fleet_invoke` | `target`, `tool`; optional `args`, `security_context`, `mode` | Runs one edge tool over a target; waits for approval |
| `http_check` | `url` (https); optional `expect_status`, `attempts`, `interval_secs` | A health gate between stages |

A refusal, a failed host or an unhealthy check fails the state, so its `on_failure` transition takes it.

The built-in workflow `infra-apply` applies one state:

1. **PLAN:** plans the state.
2. **APPLY:** applies it after your approval.
3. **VERIFY:** plans again. A converged fleet reports no change.

It records each step's changed hosts on the blackboard.

A rollout over several states is a workflow of your own, with one stage per state and an `http_check` between stages:

```yaml
states:
  CORE:
    kind: Action
    action: host_state_apply
    args: { name: "core-pod" }
    transitions:
      - { condition: on_success, target: CORE_HEALTHY }
      - { condition: on_failure, target: FAILED }
  CORE_HEALTHY:
    kind: Action
    action: http_check
    args: { url: "https://api.example.com/health", attempts: "10", interval_secs: "6" }
    transitions:
      - { condition: on_success, target: EDGE }
      - { condition: on_failure, target: FAILED }
```

Any trusted source can start it: a person in Zaru, an MCP call, another workflow, a schedule, or a signed webhook (see [Configuring Webhooks](/docs/deployment/configuring-webhooks)).
