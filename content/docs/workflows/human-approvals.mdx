# Human Approvals

Workflows can pause at any point to wait for a human decision before proceeding. The orchestrator holds the workflow execution open, notifies via the approval API, and resumes or terminates based on the response — all with configurable timeouts.

---

## Defining an Approval Gate

Add a `kind: Human` state to your workflow manifest:

```yaml
states:
  GENERATE_DRAFT:
    kind: Agent
    agent: draft-agent
    input: "{{input.topic}}"
    transitions:
      - condition: always
        target: AWAIT_APPROVAL

  AWAIT_APPROVAL:
    kind: Human
    prompt: "Review the draft in {{GENERATE_DRAFT.output}}. Answer yes to publish, no to discard."
    timeout: 86400s             # 24 hours; 3600s when omitted
    default_response: "no"      # optional; the answer taken if the timeout elapses
    transitions:
      - condition: input_equals_yes
        target: PUBLISH
      - condition: input_equals_no
        target: DISCARD

  PUBLISH:
    kind: Agent
    agent: publish-agent
    input: "{{GENERATE_DRAFT.output}}"
    transitions: []

  DISCARD:
    kind: System
    command: "echo 'Draft discarded'"
    transitions: []
```

### `kind: Human` Fields

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `prompt` | string | — | Text displayed to the reviewer. Supports Blackboard template syntax. |
| `timeout` | string | `3600s` | How long to wait for an answer, set on the state beside `transitions`. |
| `default_response` | string | — | The answer taken when `timeout` elapses with none. Without it, the workflow fails. |

A gate's answers come from its transitions: `input_equals_yes` takes `yes` (also `y` or `1`), `input_equals_no` takes `no` (also `n` or `0`), and `input_equals` takes its `value`. An answer no transition takes, such as `approved` at a yes-or-no gate, is refused and the gate is asked again.

## Listing Pending Approval Requests

Poll the approval queue from any HTTP client:

```bash
curl https://your-aegis-node/v1/human-approvals \
  -H "Authorization: Bearer $KEYCLOAK_JWT"
```

Response:

```json
{
  "pending_requests": [
    {
      "id": "req-uuid",
      "execution_id": "exec-uuid",
      "prompt": "Review the draft in <draft content>. Answer yes to publish, no to discard.",
      "created_at": "2026-03-05T14:00:00Z",
      "timeout_seconds": 86400
    }
  ]
}
```

Fetch a specific request:

```bash
curl https://your-aegis-node/v1/human-approvals/req-uuid \
  -H "Authorization: Bearer $KEYCLOAK_JWT"
```

## Approving a Request

```bash
curl -X POST https://your-aegis-node/v1/human-approvals/req-uuid/approve \
  -H "Authorization: Bearer $KEYCLOAK_JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "feedback": "Looks good, approved for production.",
    "approved_by": "alice@example.com"
  }'
```

Both fields are optional. Response:

```json
{ "status": "approved" }
```

The workflow immediately resumes from the `AWAIT_APPROVAL` state and transitions to the `approved` target state (`PUBLISH` in the example above).

---

## Rejecting a Request

```bash
curl -X POST https://your-aegis-node/v1/human-approvals/req-uuid/reject \
  -H "Authorization: Bearer $KEYCLOAK_JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "reason": "Draft needs more citations before publishing.",
    "rejected_by": "bob@example.com"
  }'
```

`reason` is required. Response:

```json
{ "status": "rejected" }
```

The workflow transitions to the `rejected` target state (`DISCARD` in the example).

## Timeout Behaviour

When `timeout` elapses without an answer:

- **No `default_response` (default):** The workflow execution fails with `Human input timeout`. No transition occurs.
- **`default_response` set:** The gate takes it as the answer, so `default_response: "no"` follows the `input_equals_no` transition. Useful when a missing response should be treated as a "no".

---

## Answering a Gate

When a run reaches a `kind: Human` state, the worker posts a `HumanInputRequested` workflow event for the gate. Besides the rendered `prompt` and the state's `default_response`, the event carries `state_name`, `responses` (the words the state's `input_equals`, `input_equals_yes` and `input_equals_no` transitions take, in their order: `["yes", "no"]` for a yes-or-no gate, `[]` for a gate with no such transition, which takes any answer) and `expires_at` (one timeout after the gate's first post). A gate posted again after an answer it does not take carries the same three.

**In Zaru Web**, a gate of a run you started is one of your pending approvals: a card under the run in the conversation, an entry on the Approvals page and a card on the run's execution page, each with one button per word in `responses` ([Human Gates of a Workflow Run](/docs/zaru/chat#human-gates-of-a-workflow-run)). Zaru's companion is offered no tool that answers a gate, in any mode.

Once a gate is answered, or closes on its timeout, it stays listed: in Zaru Web under **Recent** on the Approvals page, with "You answered &lt;word&gt;." (or, for a gate that closed on its timeout, "Nobody answered; the run timed out.") and a link to the run, and the card under the run reads the same line.

**From your own client**, list the gates your runs wait at with [`GET /v1/workflow-gates?status=pending`](/docs/reference/rest-api#get-v1workflow-gates), the ones that closed with `?status=answered` (each with the word chosen, the feedback, when it closed and what the run did then), or both with `?status=any`, and answer one with [`POST /v1/workflows/executions/{id}/signal`](/docs/reference/rest-api#post-v1workflowsexecutionsidsignal), or with `aegis.workflow.signal`, which Zaru's MCP server lists to external MCP clients such as Claude Code.

A gate is listed as pending while it is the latest event the workflow's worker posted for the run. Rows the orchestrator records for the run itself, such as its `repository_prepared` row, stay in the run's history and its logs route and never hide a pending gate, even when they follow it.

```bash
curl https://your-aegis-node/v1/workflow-gates?status=pending \
  -H "Authorization: Bearer $KEYCLOAK_JWT"

curl -X POST https://your-aegis-node/v1/workflows/executions/exec-uuid/signal \
  -H "Authorization: Bearer $KEYCLOAK_JWT" \
  -H "Content-Type: application/json" \
  -d '{ "response": "yes", "feedback": "Keep the flag name short." }'
```

## Building an Approval UI

A minimal polling loop for a custom approval interface:

```typescript
const ORCHESTRATOR = 'https://your-aegis-node';
const TOKEN = process.env.KEYCLOAK_JWT;

async function pollApprovals() {
  const res = await fetch(`${ORCHESTRATOR}/v1/human-approvals`, {
    headers: { Authorization: `Bearer ${TOKEN}` },
  });
  const { pending_requests } = await res.json();

  for (const req of pending_requests) {
    console.log(`[${req.id}] ${req.prompt}`);
    console.log(`  Created: ${req.created_at}  Timeout: ${req.timeout_seconds}s`);
  }
}

async function approve(requestId: string, feedback?: string) {
  await fetch(`${ORCHESTRATOR}/v1/human-approvals/${requestId}/approve`, {
    method: 'POST',
    headers: {
      Authorization: `Bearer ${TOKEN}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({ feedback, approved_by: 'current-user@example.com' }),
  });
}

async function reject(requestId: string, reason: string) {
  await fetch(`${ORCHESTRATOR}/v1/human-approvals/${requestId}/reject`, {
    method: 'POST',
    headers: {
      Authorization: `Bearer ${TOKEN}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({ reason, rejected_by: 'current-user@example.com' }),
  });
}
```

## Template Variables in Prompts

The `prompt` field in a `kind: Human` state supports Blackboard template syntax, giving reviewers access to outputs from earlier workflow states:

```yaml
AWAIT_APPROVAL:
  kind: Human
  prompt: |
    Agent produced the following output:
    
    {{GENERATE_DRAFT.output}}
    
    Score from quality check: {{QUALITY_CHECK.output.score}}
    
    Answer yes or no.
```

See the [Template Syntax Reference](/docs/reference/template-syntax) for the full variable namespace.
